# S3

Module comment for S3.h / S3.cpp.

## s3

The client for object stores that speak the S3 protocol: Amazon S3 and the many services that
copy it (Backblaze B2, Wasabi, MinIO and others). It offers the same functions as the WebDAV
client (WebDav.md#webdav). The account carries the endpoint in `url_`, the access key in
`user_`, the secret key in `password_` and the region (SshAccount.md#s3).

## paths

The first segment of a path is the bucket, the rest the key of an object: `/photos/2026/a.jpg`
is the object `2026/a.jpg` in the bucket `photos`. The root lists the buckets, so a bucket is
chosen like a folder and the account needs no field for it. Buckets are never created or
removed; that belongs to the provider's console, where region and access rules are decided.

## addressing

A request names the bucket either in the path (`https://endpoint/bucket/key`) or in the host
name (`https://bucket.endpoint/key`). The path style is what the copies of S3 understand and
is used for them. Amazon itself is addressed in the host style, which it asks for; an endpoint
is taken for Amazon's when its host ends in `.amazonaws.com`.

## signature

Every request is signed with AWS Signature Version 4: a canonical form of the request (method,
encoded path, sorted query, the host header and every `x-amz-` header) is hashed, and the hash
is signed with a key derived from the secret key, the date, the region and the service name.
The request is put together completely before it is signed, because every signed header has
to be sent exactly as signed. The region has to be the one the endpoint belongs to; "us-east-1"
stands in when the account names none, which is what most copies of S3 accept.

## unsigned-payload

The content is not included in the signature ("UNSIGNED-PAYLOAD"). Hashing it would mean
reading every file twice, once for the hash and once to send it. The connection is encrypted,
which protects the content on the way; the signature still protects everything else.

## errors

An error answer is XML with a `Message`; the message goes into the exception, since it names
the cause the status alone does not ("The request signature we calculated does not match", "The
bucket does not exist"). A refused HEAD has no body and is reported as access denied.

## modification-time

S3 stamps an object with the time of the upload and offers no way to set another. The file's
own modification time is therefore stored with the object as the metadata `mtime`, in seconds,
the convention rclone uses, so objects written by either program compare correctly. It is read
back with HEAD and GET; an object without it reports the time of its upload.

## stat

HEAD of the object answers for a file. If there is none, the path is a folder when anything
lies below it (#directories). A bucket is asked with HEAD as well.

## directories

S3 has no folders, only keys that contain slashes. A folder exists as long as some key begins
with its name and a slash. To let an empty folder exist, an empty object named `folder/` is
written, as the consoles of the providers do; removing a folder removes that marker. The
synchronisation only removes folders it found empty.

## list

ListObjectsV2 with the folder's name as prefix and the slash as delimiter, which makes the
service return the files of that level and the names of the folders below as "common
prefixes". The folder's own marker is left out. The listing comes in pages and every page is
fetched. Names that are not plain entry names are left out (WebDav.md#entry-names).

## remove

DELETE of the object. Unlike the cloud drives S3 keeps no trash: the object is gone unless the
bucket has versioning switched on at the provider.

## move

S3 cannot rename. A file is copied to its new key on the server, without downloading it, and
the old key is deleted. The copy keeps the metadata and with it the modification time. An
existing destination is refused first. A copy can answer with status 200 and still carry an
error in its body, so the body is looked at. Folders cannot be moved this way and are refused;
single copies are limited to five gibibytes by the service.

## download

GET of the object; the local file gets the modification time from the metadata.

## upload

A file of up to sixteen mebibytes is sent with one PUT. A larger one goes up as a multipart
upload: it is announced, sent in parts of sixteen mebibytes, each answered with a tag, and
completed with the list of tags. That keeps a failure cheap and lifts the limit of five
gibibytes a single PUT has. When a part fails or the user stops the run, the upload is
abandoned on the server, which otherwise keeps the parts and charges for them.
