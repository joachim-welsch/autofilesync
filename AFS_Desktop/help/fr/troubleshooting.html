Quand quelque chose ne se passe pas comme prévu

Le premier endroit où regarder est toujours le journal. Au niveau Info, il indique ce qui a été copié et supprimé ; au niveau Debug, aussi quel fichier a été ignoré et pour quelle raison.

Un fichier n'est pas copié

  • Il est vide. Les fichiers de taille 0 sont ignorés tant que Synchroniser les fichiers vides n'est pas coché. Le journal indique « Le fichier source vide n'a pas été copié ».
  • Le caractère générique ne correspond pas, ou une exclusion s'applique, voir Créer des synchronisations.
  • La cible est plus récente que la source. Sans Copier même si le fichier cible est plus récent, elle reste intacte.
  • Source et cible sont considérées comme identiques. Si la comparaison se fait uniquement par Date, une modification du contenu sans nouvelle date de modification passe inaperçue. Dans ce cas, cochez aussi Taille ou Contenu.
  • La synchronisation n'est pas active – la case Synchronisation active n'est pas cochée.
  • Il s'agit d'un sous-dossier, mais la synchronisation est de type Dossier. Les sous-dossiers nécessitent le type Arborescence.

Des fichiers sont recopiés à chaque passage alors qu'ils n'ont pas changé

La cible enregistre la date de modification moins précisément que la source, par exemple un disque NTFS ou FAT servant de cible à un disque Linux. La copie a alors quelques fractions de seconde d'avance sur son original, et lors de la comparaison par Date, la source est considérée comme plus récente. La Tolérance en secondes de l'onglet Options règle ce problème ; elle est à 0 si quelqu'un l'a désactivée. Un décalage d'exactement une heure sur tous les fichiers indique FAT après un changement d'heure, voir là-bas.

Rien n'est supprimé dans la cible alors que l'option est cochée

  • La source est inaccessible. Un lecteur débranché, un partage non connecté ou un serveur SSH injoignable font que rien n'est supprimé. C'est voulu.
  • Le type est Fichier. L'option ne vaut que pour Dossier et Arborescence.
  • Le caractère générique ou une exclusion retire le fichier de la synchronisation – il n'est alors pas supprimé non plus.
  • Il s'agit d'un dossier. Ce sont les fichiers qui sont reproduits ; un dossier supprimé dans la source reste dans la cible.

Rien n'est synchronisé du tout

  • Le service en arrière-plan tourne-t-il ? Le service et le programme ne synchronisent pas en même temps.
  • Si Démarrer et Synchroniser une fois sont grisés, la configuration ne contient aucune synchronisation exécutable – par exemple parce que toutes sont inactives, ou parce que la source et la cible manquent.
  • La configuration a-t-elle été enregistrée après la dernière modification ?
  • Avec une source ou une cible SSH : l'autre côté répond-il ? AutoFileSync le vérifie avant chaque passage et laisse la synchronisation de côté tant que le serveur est injoignable ou que l'authentification échoue. Le journal indique alors « Chemin SSH inaccessible » avec la raison.
  • Le serveur est de retour, mais il ne se passe toujours rien. Le résultat de la vérification d'accessibilité est mis en cache, pour que chaque passage n'ouvre pas une nouvelle connexion. Après une tentative échouée, une nouvelle vérification a lieu au plus tôt après quelques secondes, et en cas de panne durable au plus toutes les cinq minutes. Il peut donc s'écouler jusqu'à cinq minutes avant qu'une connexion rétablie soit remarquée.

Une connexion SSH échoue

  • Erreur d'authentification – le nom d'utilisateur ou le mot de passe est incorrect, ou le serveur n'autorise pas la connexion par mot de passe.
  • Erreur de connexion – l'hôte ou le port est injoignable.
  • La clé d'hôte a changé – le serveur s'identifie avec une autre clé que la première fois. AutoFileSync interrompt alors la connexion. Si le changement s'explique, par exemple après une réinstallation du serveur, l'ancienne entrée doit être supprimée du fichier known_hosts de votre profil utilisateur.
  • Compte SSH introuvable – le nom avant les deux-points dans le chemin n'appartient à aucune connexion créée. Cela arrive par exemple quand une connexion a été renommée ; les synchronisations concernées pointent alors toujours vers l'ancien nom.

Dans tous ces cas, la synchronisation concernée est sautée pour ce passage : rien n'est copié ni supprimé. Les autres synchronisations continuent normalement.

Un avertissement pour un lecteur manquant apparaît – ou non

Le signalement d'une source ou d'une cible inaccessible dépend, pour chaque synchronisation, de l'option Avertir si le lecteur ou la connexion SSH manque : activée, un avertissement suit Synchroniser une fois et une ligne d'avertissement figure dans le journal ; désactivée, seule une ligne d'information. Si une synchronisation avertit et une autre non, alors que le même disque manque aux deux, l'option est réglée différemment sur elles. Tout le reste sous Lecteurs et connexions inaccessibles.

Récupérer des fichiers supprimés

Si le mode de suppression est réglé sur Déplacer vers la corbeille, les fichiers se trouvent dans le dossier de corbeille configuré, dans la structure de leur emplacement d'origine. Avec Supprimer définitivement et avec des cibles SSH, il n'existe pas de telle copie.

Si un fichier cible a été écrasé, le Principe des générations peut aider – à condition qu'il ait été activé auparavant : la version précédente se trouve alors à côté du fichier sous le nom .bak.1.
